# Issue 提交与处理

从 [新建 Issue](https://github.com/newmanspace/cim-llm-wiki/issues/new/choose) 选择表单。模板合入默认分支后才会显示；保留空白 Issue 入口，方便提交不适合既有分类的问题。GitHub 表单的字段、必填项与标签语义见 [官方文档](https://docs.github.com/en/communities/using-templates-to-encourage-useful-issues-and-pull-requests/syntax-for-issue-forms)。

## 选择模板

| 模板 | 使用场景 | 关键内容 | 自动标签 |
|---|---|---|---|
| 缺陷报告 | 已发生的错误、异常或回归 | 实际影响、版本、最小复现、期望结果 | `bug` |
| 功能需求 | 新能力或用户体验改进 | 用户问题、预期行为、验收条件 | `enhancement` |
| 质量与技术改进 | 测试缺口、兼容迁移、性能、技术债 | 当前证据、目标、验证方法 | `enhancement` |

缺陷报告无需提交者先定位根因。日志、截图与关联记录可选；无法稳定复现时应说明频率与触发条件。单个 Issue 尽量对应一个可独立验收的问题，大项可拆成关联子项。

## 公开信息与敏感数据

正文、标题和附件都会公开。只使用合成样例或脱敏片段，不提交密码、Token、Cookie、连接串、真实业务文档、个人信息、客户标识、内网地址或真实原件路径。文档溯源问题可使用 `/shared/demo/source.xlsx` 这样的合成路径说明，同时保留复现所需的路径结构、版本与校验关系。

模板中的确认项仅提醒提交者，不是自动脱敏或安全扫描。空白入口和 API 提交也不会受到表单必填校验。维护者仍需检查附件和上下文；敏感安全问题先通过团队已有的私密渠道联系维护者，不在公开 Issue 中披露利用细节。

## 建议的处理方式

1. **核对与分类**：先搜索重复项，确认影响和最小复现。维护者按实际内容补充现有的 `documentation`、`dependencies` 或 `help wanted` 等标签；模板不自动指定处理人或优先级。
2. **明确优先级**：建议先处理数据损坏、认证绕过和业务阻断，再处理局部功能缺陷，最后安排一般优化。优先级由维护者根据影响、可利用性和临时方案确定，不由提交者自报的严重程度直接决定。
3. **明确完成条件**：实现前确认可验证的验收项和责任人，尚未测量的数据标为“未测量”。依赖升级要核对最低运行时与工具链兼容性，不能仅凭版本更新或单项测试通过判断可合并。
4. **关联修复**：PR 描述关联 Issue。满足全部验收项时使用 `Closes #<编号>`；只完成部分工作时使用 `Refs #<编号>`，保留未完成项。
5. **关闭与复核**：记录修复或暂缓理由、关联 PR、验证环境与结果。代码合并不等于已经部署；若验收要求部署后验证，完成前保持 Issue 未关闭。重复、无效或不计划处理的问题说明原因，不用“完成”掩盖未实施事项。

## 建议优先建立的跟踪项

以下是候选事项，本次只建立模板，尚未自动创建这些 Issue：

- **Python 转换镜像与依赖审计**：明确镜像/依赖覆盖范围、漏洞分级与处置方式，上传脱敏报告；不把适配层单元测试视作依赖安全保证。
- **浏览器端到端测试**：用合成数据验证 Admin 基路径、认证跳转、项目管理和错误提示，并在 CI 中运行，不连接生产业务环境。
- **TypeScript 7 兼容迁移**：待 Vue/Volar 工具链支持后复核 `vue-tsc`、构建与测试，再移除已记录的版本限制。
- **Node 运行时支持矩阵**：保留最低支持版本的验证，再按维护计划增加更高受支持版本的兼容性检查；升级最低版本时同步更新类型定义、镜像与文档。
