## 1. 简介

### 1.1 业务背景

系统目前只有项目注册管理，产品是项目上的文本字段，缺少独立产品、版本文档集、可冻结的产品基线和差异继承。用户已确认一套软件产品标准目录，要求继续开发管理功能，并统一抽象产品和项目。

- [GitLab Namespaces](https://docs.gitlab.com/user/namespace/)：参考统一容器和显示名称／路径分离。
- [Redmine Project Settings](https://www.redmine.org/projects/redmine/wiki/RedmineProjectSettings)：参考父子项目、独立功能配置和版本共享的显式关系。

## 2. 需求概述

### 2.1 需求简介

以 Workspace 为文档、版本和基线的管理边界，提供产品管理与项目管理视图。支持单父级、多级继承，固定父级基线，子级覆盖和独立授权。

| 编号 | 需求 | 角色 |
|---|---|---|
| WS-01 | 创建、查询、修改、归档产品及项目工作空间 | 管理员 |
| WS-02 | 产品初始化标准目录，各目录生成 README 内容 | 产品负责人 |
| WS-03 | 目录和页面新增、改名、移动、排序及修订 | 文档维护者 |
| WS-04 | 管理产品版本及完整文档集，指定推荐正式版 | 产品负责人 |
| WS-05 | 冻结包含目录、页面、附件引用和规范修订的基线 | 发布负责人 |
| WS-06 | 产品到项目、项目到项目的多级继承 | 项目负责人 |

## 3. 需求详述

### 3.1 统一模型与命名

**规则说明**：底层使用 Workspace，中文为工作空间，类型为 product 或 project。界面主要使用产品管理、项目管理；公共设置称工作空间设置。显示名称允许空格，路径使用小写 kebab-case，身份使用稳定标识，不以层级路径作为身份。

**处理逻辑**：创建时选择类型并校验标识，按类型提供入口；保留现有项目身份和 URL 兼容映射。

**备注**：不引入组织、团队、群组等额外工作空间类型，不将版本建成 Workspace。

### 3.2 标准目录与文档

**规则说明**：产品根包含 Overview、Product Management、Pre-sales、Architecture and Governance、Product Versions 和 Templates。Templates 仅在根维护。Documentation Standards 说明规范并引用根模板。版本包含 Overview、Documentation、Engineering Documentation、Release and Delivery、Document Baselines、Related Projects。

**处理逻辑**：选择标准模板，预览目录，事务性初始化；占位版本／模块／功能不直接生成业务实体。创建真实版本时按版本模板初始化，创建模块时显式选择模块模板。

**备注**：README 是目录首页内容，不等同已完成业务文档。已有目录不覆盖、不自动搬迁历史资料。详细结构以链接模板为准。

### 3.3 版本与基线

**规则说明**：版本有开发、已发布、归档状态。版本下展示完整适用文档；文档修订与软件版本分离。推荐正式版只能引用同工作空间已发布版本。发布和交付基线不可变，文档纠错创建新修订和新基线，旧基线不覆盖。

**处理逻辑**：开发稿完成校验后冻结基线；批准发布时绑定软件清单和正式文档基线，原子切换推荐入口；项目采用明确版本与基线。

**备注**：首期支持基线创建、浏览及清单比较；任意历史内容一键恢复暂不包含，避免隐式覆盖当前草稿。

### 3.4 继承与覆盖

**规则说明**：已确认采用单父级、多级继承。首期允许 product → project、project → project；product 为根。一个子级固定一个直接父级已发布基线，父基线可已包含祖先内容。子级不实时跟随上游；覆盖不反写父级。继承范围为显式导出的目录、页面、模板与冻结的规范引用，不继承客户项目列表、发布审批、凭据或执行日志。

**处理逻辑**：选择父工作空间及其基线，预览授权导出范围并确认；建立关系。子级看到完整有效文档树，并能识别继承、覆盖、本地新增和隐藏内容。升级时比较旧父基线、新父基线及本地变更，处理冲突后提交。

**备注**：同一时点只允许一个直接继承来源；非父级产品可以作为采用关系关联，不能成为第二继承来源。跨版本继承使用明确基线，不混同于组织包含关系。

### 3.5 权限与项目关联

**规则说明**：已确认权限独立；父级成员或 Token 不因继承获得子级权限。建立继承须有子级管理权限和父基线导出授权。已授权导入的副本按子级权限管理，源资料仍受父级权限保护。全局管理员仍可管理全部工作空间，这与父子权限继承不同。

**处理逻辑**：在每次 API 和文档读取中校验目标工作空间及操作范围；关联产品版本时验证基线归属，记录有效期和升级历史。Related Projects 汇总关联项目，对无权查看的项目不披露名称或详情。

**备注**：当前只有环境配置管理员和现有项目 Token。首期以管理员及独立 Workspace Token 实施隔离；多用户账户、成员管理和角色 UI 不在本期，接口预留主体映射。

## 4. 非功能需求

| 类别 | 要求 |
|---|---|
| 一致性 | 继承关系、基线归属、版本归属和发布指针受数据库约束；并发操作不得产生环 |
| 安全 | 每次读取和写入都验证目标空间；禁止通过旧路由、静态产物和附件绕过空间权限 |
| 可靠性 | 文件与数据库发布可重试、可补偿；失败不得产生可见的半份基线 |
| 性能 | 解析基线时读取冻结清单，不随继承深度逐页递归查询；列表分页 |
| 兼容性 | 保留旧项目标识、Token 的原范围和现有编译校验，不静默放宽契约 |
| 可用性 | 移动或改名保留稳定标识；显示来源、版本和基线，避免误改父级 |

## 5. 影响范围分析

### 5.1 系统组件影响

| Go Admin API／PostgreSQL | Vue Admin | Node Knowledge Service | Wiki Core／契约 | VitePress／网关 |
|---|---|---|---|---|
| ✓ | ✓ | ✓ | ✓ | ✓ |

### 5.2 周边系统影响

不需要调用或修改 GitLab、Redmine、SAP、Oracle 服务；只参考其组织方式。文件存储和现有 Docker 部署涉及挂载及服务间授权调整，实际部署需另行批准。

### 5.3 功能模块影响

产品和项目列表、详情、版本、文档导航、基线、知识摄取上下文、Token 校验和静态发布均受影响。

### 5.4 数据影响

新增工作空间、版本、关系、目录、页面修订、基线、采用关系和审计数据。既有项目一对一迁移为 project 工作空间；产品文本仅保留为历史信息，不据此自动合并出产品实体。文件原位保留，通过显式映射接入。

### 5.5 用户影响

保留项目入口，增加产品管理和父级基线选择。维护者需理解开发稿、正式文档、继承覆盖及固定交付基线；以页面提示和 README 说明，不预设培训或通知动作。

## 6. 依赖与约束

依赖 PostgreSQL、现有认证、Go 管理 API、Node 核心和 VitePress。需先评审统一模型和 Wiki 映射，再编码；不直接把静态模板复制进受严格校验的知识目录。继承深度首期上限建议为 16，作为可配置技术限额，不改变单父级多级规则。无用户指定交付时间。

## 7. 附录
