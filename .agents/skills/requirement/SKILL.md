# 需求分析 (Requirement)

本技能将一个模糊的业务想法，转化为一份结构化的需求文档（URD）。它是整个产研流程的起点，在动手设计之前必须先明确"做什么"和"为什么做"。

## 前置约束（提问驱动与需求澄清）

在接到需求并开始撰写文档前，**必须严格执行以下前置动作**：

1. **主动提问澄清**：向用户提出 2 到 3 个关于业务背景的澄清问题：
   - 这个需求要解决什么问题？当前现状是什么？期望达到什么效果？
   - 期望的输入/输出是什么？有哪些边界条件？
   - 是否有现有的参考系统或竞品？
   - **必须等待明确回答后，才能开始撰写文档。**

2. **影响范围分析**：主动向用户澄清需求的影响范围，包括但不限于：
   - **周边系统影响**：是否涉及与外部系统的交互变更？上下游接口是否需要联动调整？
   - **功能模块影响**：当前系统中哪些已有模块会被影响？是否需要修改现有功能？
   - **数据影响**：是否涉及数据结构变更、数据迁移、新增数据表？
   - **用户影响**：是否影响现有用户的使用流程？是否需要用户培训或通知？

3. **项目上下文嗅探**：读取项目结构，了解当前系统能力边界，避免提出与现有架构冲突的需求。

## 文档架构与输出标准

在获得澄清问题的回答后，基于诉求出具一份结构化的需求文档，存放路径遵循 `docs/development/features/` 目录下的命名规范（前缀 `urd-`，小写 kebab-case，如 `urd-<name>.md`）。

文档内容应当严格遵守 URD 文档骨架（参见 `assets/user-requirements-template.md`）：

| 章节 | 说明 |
|------|------|
| 1. 简介 | 业务背景、参考资料 |
| 2. 需求概述 | 需求简介、需求列表（含用户角色） |
| 3. 需求详述 | 各需求模块的规则说明、处理逻辑、备注 |
| 4. 非功能需求 | 性能、安全、兼容性、可用性 |
| 5. 影响范围分析 | 系统业务影响矩阵、周边系统、功能模块、数据、用户 |
| 6. 依赖与约束 | 上下游依赖、技术约束、时间约束 |
| 7. 附录 | 补充材料、术语表 |
| 8. 签核意见 | 需求提出人、开发、测试、项目经理签核 |

### 需求详述章节要求

- **规则说明**：每个需求模块必须列出具体的业务规则或逻辑
- **处理逻辑**：使用步骤化描述处理流程
- **备注**：补充说明保留原有逻辑、例外情况等

### 影响范围分析要求

- **系统矩阵**：使用表格列出所有相关系统，在受影响的系统下方标记 ✓
- **周边系统**：列出受影响的外部系统及具体影响点
- **功能模块**：列出受影响的内部模块及变更范围
- **数据**：说明数据层面的影响（新增/变更/迁移）
- **用户**：说明对现有用户流程的影响程度

## 输出动作

生成一份标准的 `URD Document`（参见 `assets/user-requirements-template.md`），包含上述核心章节。

状态标记：
- ✅ **Approved** — 需求明确，可进入设计阶段
- ⚠️ **Needs Clarification** — 需补充说明
- ❌ **Rejected** — 需求不合理或超出范围

## 与其他技能的协作

| 下游技能 | 关系 |
|----------|------|
| `design` | URD 批准后，调用 design 技能产出 SDD 架构设计文档 |
| `github-issue` | URD 完成后，在 GitHub 创建对应的功能需求 Issue |
