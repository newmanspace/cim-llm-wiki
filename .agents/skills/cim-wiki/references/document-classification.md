# 文档类型判定与格式选择

## 先判定类型，再匹配模板

阅读源文标题、用途、正文结构、表头和内容，判断它实际是什么文档；文件扩展名、所在目录和可用模板只能辅助判断，不能代替内容判定。随后检查 Project 生效模板是否专门覆盖这一类型和用途，而不是选择名称最接近、最容易通过检查的模板。

| 情况 | 处理 |
| --- | --- |
| 有语义匹配的专门模板 | 记录匹配依据，按该模板重排源内容，检查对应正文与目录契约 |
| 无专门模板 | 保持实际类型，按通用标准格式整理，执行适用的格式和保真检查 |
| 实际类型仍有关键歧义 | 保留源文结构完成可确定的格式整理；说明歧义，需要改变内容性质时再询问 |
| 用户明确要求把资料改编为另一类文档 | 按授权进行改编，区分源文事实与待确认的新编内容；这属于文档新编，不是忠实转换 |

“无专门模板”不等于“源内容不完整”：实际属于 URD、SDD 等且有匹配模板时，仍按该类型处理真实缺项，不能转用通用格式逃避模板检查。

功能清单即使列有模块和功能描述，也不因此成为 URD。没有功能清单专门模板时，保留模块、子模块、原有功能序号、描述和备注，按标准格式整理；不能套 URD 补出 REQ/AC 编号、优先级、用户场景、非功能需求或验收矩阵。模板里有必填章节，也不构成改变源文类型的理由。

同样，统计表、检查清单或会议纪要不能仅因内容相关就套成测试报告、Runbook 或 SDD。判断依据是文档的实际用途，不是它能为哪一类交付提供素材。交付契约仍缺 URD／SDD 时，分别记录缺项，不能靠更名或新增占位内容制造满足。

在转换清单或独立报告记录实际类型、判断依据、专门模板匹配结果和格式模式；这些分析不写进业务正文。用户仅同意落盘路径或某项候选方案，不应被解释为主动要求类型改编；发现先前判断错误时应明确纠正，而不是沿用错误模板。

## 无专门模板时的标准格式

标准格式是文档的公共外观和信息规范，不是另一份业务内容模板：

- 使用 Project 生效的通用 Markdown 格式和公共文档信息要求，统一标题、必要的文档信息、层级、编号、表格、代码块、图片、参考文档及修订记录；没有项目公共规定时采用清晰的一致格式，不虚构服务契约。
- 保留源文实际标题、章节含义、表格列、原有编号、合并单元格语义、单位、限定条件、备注及图表关系；允许修正明确的排版错误，不为套骨架增删业务内容。
- 需要的公共信息缺失时可简洁写“待确认”。不得把专门模板的必填章节、业务编号或验收要求搬来，再批量填“待确认”；这仍属于强行套模板。
- 来源、哈希、版本证据和必要转换说明集中在参考文档，分析和问题放在独立报告，遵守 Skill 的正文边界。
- `template_id` 保持为空／未匹配，不创建 `standard` 等虚构模板，不借用 `glossary`、`product` 或其他模板作为通用壳。

## 检查与服务边界

检查源内容覆盖、格式一致性、表格列与记录、编号和单位、引用、图片／Mermaid 渲染及敏感认证信息处理；逐项报告实际结果。

专门模板和通用格式均使用本地 ingest 工具检查；无专门模板时省略 template_id，不调用服务端 check-document。模板契约检查记为“不适用”，公共格式和保真核对分别记录实际结果。缺少完整项目规则时明确未验证项，不提交其他模板取得通过结果。

保存路径按[无专门模板的路径规则](document-routing.md#无专门模板的标准格式文档)处理。缺少服务登记类型不阻断本地标准格式转换，但不能跳过归类、审核和发布门禁，或以修改模板绑定解决此次转换。
